LLM Agent 与 Harness 工程 · 第 02 课

Agent Loop：思考-行动-观察循环是怎么跑起来的

本课你会得到一个精确的心智模型：一轮循环的完整步骤、工具调用的数据流、循环何时终止、以及它为什么会失控。掌握这些，你就能看懂任何 Agent 产品 80% 的行为。

前置知识：Harness 概览（第一课）

0. 最重要的一个心智模型

先记住一句颠覆直觉的话：大模型本身什么都执行不了。它不能读文件、不能上网、不能运行命令——它只能输出文字。所有"行动"都是由 Harness 代劳的。

所以 Agent Loop 的本质极其朴素：一个 while 循环。Anthropic 官方文档称之为 agentic loop——LLM 在循环里不断"看环境 → 做决定 → 产生行动意图"，Harness 负责把意图变成真实动作，再把动作结果喂回去。[1]

while (任务未完成) {
    模型输出 = 调用模型(完整上下文);
    if (模型输出包含工具调用) {
        结果 = Harness执行工具(调用参数);
        把结果追加进上下文;          // 这就是"观察"
    } else {
        任务完成;                    // 模型给出了最终回答
    }
}

就这么几行。所有让人眼花缭乱的 Agent 产品，内核都是这个循环的变体。

1. 一轮循环的完整步骤

把镜头放慢，一轮完整迭代有 7 个步骤：

  1. 组装上下文：Harness 把系统提示词、工具清单（每个工具的名称、描述、参数 schema）、全部历史消息打包成一次 API 请求。
  2. 模型推理（思考）：模型阅读上下文，决定下一步——是调用某个工具，还是直接回答用户。
  3. 输出解析：Harness 检查模型输出：是普通文本，还是结构化的工具调用请求？
  4. 安全关卡：执行前，Harness 检查权限——这个操作是否需要用户确认？（比如删除文件）这是 Harness 的产品决策点。
  5. 工具执行（行动）：Harness（不是模型！）在真实环境里执行：读文件、跑命令、调 API。
  6. 结果回填（观察）：执行结果（成功输出或报错信息）作为一条新消息追加进对话历史。
  7. 终止检查：Harness 判断：模型是否决定结束？是否超出轮数/时间/费用上限？没结束就回到第 1 步，进入下一轮。
PM 视角注意第 4 步——"何时打断模型、向用户要确认"是纯产品决策。确认太少，用户害怕失控；确认太多，Agent 的体验退化成弹窗地狱。这是 Agent 产品信任设计的核心张力。

2. 工具调用的数据流：模型只写"申请单"

这是新手最容易误解的地方。模型调用工具的过程，更像填一张申请单交给 Harness 审批执行，而不是自己动手。看一个真实的消息序列（简化自 Anthropic 文档 [1]）：

// 第 1 次请求：用户的问题 + 可用工具清单
用户: "utils.py 这个文件有多少行？"

// 模型的回复——不是答案，而是一张"申请单"
模型: tool_use: {
        name: "count_lines",
        input: { path: "utils.py" }
      }
// ↑ 模型到这里就停了。它不知道也不关心这个工具怎么运行

// Harness 拿到申请单：校验参数 → 执行 → 拿到结果
// 第 2 次请求：Harness 把结果塞回历史，再次调用模型
tool_result: "128"

// 模型这才给出最终回答
模型: "utils.py 共有 128 行。"

三个关键结论：

  • 模型输出的是结构化意图（工具名 + JSON 参数），真正的执行永远发生在 Harness 侧。所以工具的参数校验、权限控制、错误处理全在 Harness 手里——这是你的工程团队的主战场。
  • 每一轮迭代，Harness 都要把完整历史重新发给模型。模型没有记忆，它的"记忆"就是不断变长的消息列表。这直接导致两个后果：上下文越滚越大（成本和性能问题）、以及旧信息永远在影响模型（上下文工程问题的根源，下一课的主题）。
  • 工具描述本身就是提示词。模型靠工具的名称和描述来决定"用不用、怎么用"。描述写得含糊，模型就会用错——工具文档的质量直接决定 Agent 的成功率。[2]

3. 循环何时终止？

一个会自己决定"下一步做什么"的系统，必须有刹车。终止条件分两类：

模型主动终止（理想情况）

模型认为任务完成，输出最终回答而不再请求任何工具。API 层面会返回一个终止标记（如 stop_reason = end_turn）。[1]

Harness 强制终止（保底机制）

机制含义PM 要定义的产品问题
最大轮数循环 N 轮仍未结束，强制停止N 设多少？简单问答 5 轮够了，复杂编程任务可能要上百轮
预算上限累计 token 消耗或费用超阈值即停单任务成本上限是多少？超了是报错还是降级？
超时单步或整体耗时超限用户的耐心阈值——等多久算"卡住了"？
用户中断用户随时喊停或修改指令中断后是丢弃全部进度还是可恢复？
错误熔断连续失败若干次后停止重试失败几次算"这条路走不通"？
专家细节"模型认为自己完成了"≠"任务真的完成了"。模型可能在任务只做了一半时就输出 end_turn。所以严肃的 Agent 产品还会加结果校验（比如改完代码后跑一遍测试），这属于下一站"Agent 评估"的话题。

4. 常见失败模式与应对

专家和普通人的区别，是知道这个循环会以哪几种方式崩坏。五种最常见：

失败模式表现根因应对
死循环 模型反复执行同一个无效操作，轮数暴涨、费用失控 模型无法从错误信息中学到"换条路" 轮数上限 + 重复动作检测（Harness 发现同一调用出现多次就注入提醒）
幻觉工具调用 调用不存在的工具，或参数格式错误、编造文件路径 模型对工具集理解模糊，"想象"出合理但不存在的接口 工具描述写清楚边界；Harness 校验失败时把"为什么错"讲明白再还给模型重试
目标漂移 做着做着忘了原始任务，开始修无关的东西 上下文越长，初始指令的影响力被稀释 把用户目标固定在系统提示词里；长任务拆成多个短循环分段执行
上下文爆炸 任务中后期突然变慢、变贵、变笨 历史消息超过窗口上限，被粗暴截断，关键信息丢失 上下文压缩/摘要、按需检索而非全量塞入——这是上下文工程的核心
错误信息反噬 工具报错后模型开始乱试，越修越错 报错信息是给人看的，不是给模型看的，模型读不懂 为模型重写错误信息：说清楚发生了什么、建议下一步——工具设计的一部分[2]

5. 回到你的角色：PM 能做什么

理解了 Agent Loop，你就拿到了 Agent 产品最重要的几个观测指标：

  • 平均循环轮数——同类任务的轮数突然上升，通常是工具或提示词退化了的早期信号
  • 任务完成率 vs 模型自认完成率——两者的差距就是"需要加结果校验"的证据
  • 单任务成本——每轮都在重发全部历史，轮数 × 上下文长度 ≈ 费用
  • 用户中断率——用户在循环中途叫停的比例，反映信任与体验问题
