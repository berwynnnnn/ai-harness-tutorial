LLM Agent 与 Harness 工程 · 第 04 课（路径收官）

Agent 评估：把"感觉变差了"变成数字

第 02 课埋过一个钩子："模型自认完成 ≠ 任务真完成"。这一课收网——如何系统地度量 Agent 到底行不行。评估（Evals）是 PM 在 Agent 领域最能直接创造价值的地方：定义"什么算成功"本来就是产品经理的本职。

前置知识：Agent Loop · 上下文工程

0. 没有评估会发生什么

Anthropic 描述了一个几乎每个 Agent 团队都经历过的崩溃点[1]：

早期靠手工测试、内部试用和直觉，产品能走得很远。但当 Agent 上线、用户变多后，某天用户开始抱怨"这次更新后它变笨了"——而团队无法验证：是模型变了？提示词改了？还是用户的感觉有偏差？于是进入" reactive 循环"：等投诉 → 手工复现 → 修一个 bug → 祈祷没修坏别的。

PM 视角评估的价值是复利式的：早期它强迫团队把"成功"定义清楚（两个工程师读同一份需求文档，对边界情况的理解可以完全不同，评估套件能消除这种歧义）；后期它是回归测试、是换模型时的快速体检（有评估的团队几天完成模型升级，没有的要测几周）、也是产品与研究团队之间带宽最高的沟通渠道。

1. 先学会行话：评估的七个术语

这套术语来自 Anthropic 官方定义[1]，是你和工程师对等对话的基础：

术语含义一个客服 Agent 的例子
任务 Task一个有明确输入和成功标准的测试"愤怒用户要求退款，金额 ¥80"
尝试 Trial对一个任务的一次执行（模型有随机性，要多跑几次）同一退款场景跑 5 次
评分器 Grader给表现的某个方面打分的逻辑"退款是否实际到账"检查
轨迹 Transcript一次尝试的完整记录：输出、工具调用、推理Agent 的完整对话+操作日志
结果 Outcome尝试结束时环境的真实状态数据库里真的存在这条退款记录（而不只是 Agent 说了句"已退款"）
评估套件 Suite围绕同一能力目标的一组任务退款、取消、升级三个场景的集合
评估框架 Eval harness端到端跑评估的基础设施并发跑任务、记录轨迹、汇总分数

特别注意 Transcript 和 Outcome 的区别——这正是第 02 课钩子的答案：机票 Agent 说"已为您订好机票"（轨迹），但数据库里有没有真实预订记录（结果）才是真相。评结果，别只听 Agent 说什么。

2. 三种评分器：能用代码判的，别用模型判

类型例子优点缺点
代码评分器 单元测试、字符串匹配、状态检查、工具调用校验 快、便宜、客观、可复现 死板：合理但不完全匹配预期的答案会被误杀
模型评分器（LLM-as-judge） 按评分细则给"语气是否共情"打分、成对比较 灵活，能评开放性任务 不确定、更贵，必须用人工校准过才可信
人工评分器 领域专家审阅、抽查、标注一致性检查 金标准 贵、慢、难规模化

官方建议的优先级：能用确定性评分器就用，需要灵活性才上 LLM 评分器，人工评分器用于校准和抽查。一个实用的 LLM 评分器技巧：给模型留退路——允许它回答"信息不足，无法判断"，能显著减少评分幻觉。

3. 两套评估各司其职：能力评估 vs 回归评估

能力评估 Capability回归评估 Regression
问的问题"这个 Agent 还能做好什么？""它以前会的，现在还会吗？"
通过率预期故意从低开始——给团队一座要爬的山接近 100%——下降即报警
生命周期通过率变高后"毕业"，转入回归套件持续运行，捕捉漂移

4. 处理不确定性：pass@k 与 pass^k

Agent 每次跑的结果都可能不同，所以单次成败说明不了问题。两个指标要记牢：

  • pass@k：跑 k 次，至少成功一次的概率。k 越大分越高。适合"多试几次只要成一次就行"的工具型场景。编码领域最看重 pass@1（一次就成）。
  • pass^k：跑 k 次，全部成功的概率。k 越大分越低——单次 75% 成功率的 Agent，连跑 3 次全过的概率只有 0.75³ ≈ 42%。
PM 视角选哪个指标由产品形态决定：面向用户的客服 Agent 必须用 pass^k 思考（用户要求每次都可靠）；内部批处理工具用 pass@k 就够。向工程师要数字时先问清楚是哪一个——这两个数字能差出好几倍。

5. 从零到一的路线图（官方八步的精华）

  1. 尽早开始，别等完美：20-50 个来自真实失败案例的任务就是极好的起点。越晚开始，越要从线上系统反推成功标准。
  2. 从手工测试和 bug 清单取材：把用户报过的失败直接转成测试用例，按用户影响排优先级。
  3. 任务必须无歧义：好任务的标准是"两个领域专家独立判断会得出相同结论"。模糊的任务 = 指标里的噪音。
  4. 评结果，不评路径：别检查"Agent 是否按特定顺序调用了工具"——Agent 经常找到出题人没想到的有效路径，过度限制步骤只会惩罚创造性。
  5. 设计部分得分：正确识别了问题、验证了身份、但退款没处理成功——这明显好于第一步就失败，分数应体现这个连续谱。
  6. 防作弊：任务和评分器要让"通过"只能靠真正解决问题，堵死钻空子的路。
  7. 读轨迹！：不读 transcript 就不知道是 Agent 真错了，还是你的评分器误杀了好答案。官方原话：在有人读过轨迹之前，不要轻信任何评估分数。
  8. 警惕评估饱和：通过率 100% 的评估只能防回归、不能再指引进步，该换更难的题了。

6. 评估不是唯一防线：瑞士奶酪模型

自动化评估跑在上线前（每次改动、每次换模型都跑）；但没有任何一层能拦住所有问题，完整的图景是多层叠加[1]：

  • 生产监控——上线后的真实行为分布，暴露合成评估没覆盖的场景（但问题已经触达用户了）
  • A/B 测试——用真实流量验证重大改动（慢，但测的是用户结果）
  • 用户反馈——暴露你没预料到的问题（稀疏、偏向严重问题）
  • 人工轨迹审阅——每周抽样读轨迹，校准"什么是好"的直觉
  • 系统性人工评估——留给校准 LLM 评分器和主观性强的任务

7. 回到你的角色：PM 是评估的第一作者

这是全课程里最直接的行动号召——Anthropic 原文明确写道："离产品需求和用户最近的人最适合定义成功"，并鼓励产品经理直接参与贡献评估任务[1]。你可以：

  • 用评估任务压力测试需求：写不出评估任务的 PRD，说明需求还不够具体
  • 主持"成功标准"工作坊：把客服、销售拉进来定义三个问题——不破坏事情、做了我要求的事、做得好（这是视频编辑产品 Descript 的三维框架）
  • 把 bug 清单变成评估资产的流程固化下来：每个线上事故复盘时问一句"它能变成一个测试用例吗？"
  • 要求团队区分 pass@k 和 pass^k 汇报，并为面向用户的功能守住 pass^k 底线

毕业小结：你已经拥有的心智地图

四课下来，你手里有了一张完整的 Agent 产品地图：

  1. Harness 概览：模型只是大脑，Harness 让它干活；产品差异的主战场在 Harness。
  2. Agent Loop：一切的内核是 while 循环；模型只输出意图，执行在 Harness 侧；失败有五种经典崩坏方式。
  3. 上下文工程：上下文是稀缺的注意力预算；治理靠最小化、压缩、笔记、子 Agent。
  4. Agent 评估：定义成功、度量成功、守护成功；这是 PM 的主场。

下一步建议从"知识"走向"智慧"：拿你真实接触的 Agent 产品做解剖——它的一轮循环是什么样的？失败时会怎样？有什么评估手段？随时把你的分析拿来和我对练。
