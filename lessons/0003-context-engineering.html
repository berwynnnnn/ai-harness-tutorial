LLM Agent 与 Harness 工程 · 第 03 课

上下文工程：治理模型有限的"注意力预算"

上一课我们知道：每轮循环都在重发全部历史，上下文只会越滚越大。这一课回答"怎么办"——上下文工程（Context Engineering）是当下 Harness 工程中最核心的战场，也是你作为 PM 理解 Agent 产品质量差异的钥匙。

前置知识：第 02 课 · Agent Loop

0. 从提示词工程到上下文工程

先明确定义（来自 Anthropic 官方[1]）：

提示词工程 Prompt Engineering上下文工程 Context Engineering
关心什么怎么写好指令（主要是系统提示词）推理时刻进入模型的全部 token 如何被策划和维护：系统指令、工具、外部数据、历史消息……
时机一次性写好每次决定"给模型看什么"时都在迭代
类比写一份岗位说明书管理一位员工每天实际接触到的所有信息流

一句话：上下文工程 = 从不断膨胀的信息海洋里，为每次推理挑出最可能产生期望行为的那一小组 token。

1. 为什么必须治理？上下文腐化与注意力预算

你可能会问：上下文窗口越来越大（20 万、100 万 token），塞进去不就行了？不行。这里有两个经过实证的概念：

上下文腐化（Context Rot）

"大海捞针"类基准测试反复发现：随着上下文变长，模型准确召回信息的能力持续下降。这不是某一家模型的问题，而是所有模型都存在的共性。[1]

注意力预算（Attention Budget）

根因在架构：Transformer 里每个 token 都要"注意"所有其他 token，n 个 token 就有 n² 组关系。上下文越长，注意力被摊得越薄。所以模型像人一样有有限的"工作记忆"——上下文是边际收益递减的稀缺资源，不是越大越好。

PM 视角这解释了你在产品里见过的怪现象：Agent 在任务前段聪明、后段犯蠢——不是模型"累了"，是它的注意力预算被无关历史耗光了。"等更大的上下文窗口就能解决"是错误预期：官方判断是，可预见的未来里任何尺寸的窗口都会受上下文污染影响。

2. 上下文的组成：每一块都要"少而精"

上下文工程的指导原则只有一句话：找到最小的、高信号的 token 集合。落到各组成部分：

组成部分常见错误正确姿势
系统提示词越写越长，堆满边界情况规则用最小提示起步，按观察到的失败模式逐步补充；分节组织（XML 标签/Markdown 标题）
工具集工具膨胀：功能重叠，模型分不清该用哪个最小可用工具集；"人类工程师都分不清该用哪个工具时，模型更分不清"
示例（few-shot）塞一长串边界情况清单少量、多样、有代表性的典型示例——"胜过千言的图片"
消息历史全量保留，越滚越大下一节专门讲

3. 获取上下文的两条路线：预取 vs 即时检索

除了控制已有内容，还要决定"新信息怎么进来"：

  • 预计算检索（Pre-inference retrieval）：推理前就把相关内容捞出来塞进上下文——典型代表是 RAG（基于向量的检索）。快，但可能塞进大量无关内容，且索引容易过期。
  • 即时检索（Just-in-time retrieval）：让 Agent 在循环中自己按需探索——搜索、读文件、看目录结构。慢一点，但支持渐进式披露（progressive disclosure）：每次交互只拉入当前需要的信息，文件名、目录层级、时间戳本身都在提供线索。

实践中的赢家往往是混合策略：关键信息（如项目约定文件）预先塞入，其余靠 Agent 按需探索。Claude Code 就是这种混合模型的代表。[1]

4. 长任务的三件法宝

当任务长达数十分钟到数小时（大型代码迁移、深度研究），token 必然超过窗口上限。业界收敛出三种技术，建议牢记它们的名字和适用场景：

技术机制适合的任务
压缩（Compaction） 上下文快满时，让模型把历史总结成摘要，用摘要开新窗口继续。Claude Code 会保留架构决策、未解决的 bug，丢弃冗余的工具输出，并带上最近访问的 5 个文件 需要连续来回对话的任务
结构化笔记（Structured note-taking） Agent 定期把关键状态写成笔记存到上下文之外（文件/记忆系统），之后再读回来。相当于 Agent 自带记事本 有明确里程碑的迭代型任务
子 Agent 架构（Sub-agents） 主 Agent 只做高层协调，派子 Agent 用干净的上下文做深度探索——子 Agent 可能烧掉数万 token，但只返回 1-2 千 token 的浓缩结论 可并行的复杂研究与分析
专家细节压缩的难点在于"留什么、丢什么"：压得太狠，会丢掉当时不重要、后来才关键的信息。官方建议从"宁多勿漏"起步调优。另外有个低风险的轻量手段：工具结果清理——深层历史里原始的工具输出早已无用，可以安全删掉。

5. 另一种声音：别把上下文管理外包给编排

学习一个领域要到专家级，必须知道主流之外的观点。Cognition（Devin 的团队）在《Don't Build Multi-Agents》中提出两条著名原则[2]：

  • 共享上下文：多个 Agent 各自持有一部分的上下文时，会做出互相矛盾的决策——因为"行动携带着隐含的决策"，一个 Agent 不知道另一个 Agent 为什么那样做。
  • 慎用多 Agent：很多团队用多 Agent 来"分摊上下文"，结果引入更大的上下文同步难题。单 Agent + 好的上下文压缩往往更可靠。

这和 Anthropic 推荐的子 Agent 架构矛盾吗？不完全——关键区别在于任务类型：并行探索型任务（检索、研究）适合子 Agent；顺序决策型任务（写一个连贯的代码改动）则应该由单一上下文持有者完成。能说出这层区别，你就是专家了。

6. 回到你的角色：PM 能做什么

  • 把"上下文"当成产品资源来度量：上下文利用率、压缩触发频率、压缩后任务的续跑成功率，都是可埋点的指标。
  • 警惕"工具膨胀"提案：每次有人想给 Agent 加新工具，问一句"它和现有工具的边界是什么？人类能一句话说清吗？"——工具集膨胀是成功率下降的常见根因。
  • 长任务体验设计：用户能不能看到 Agent 的"记事本"（任务清单、进度笔记）？把上下文管理可视化，是 Agent 产品信任感的重要来源。
  • 对"更大窗口"祛魅：当有人用"换更大上下文窗口的模型"来回应质量问题时，你可以指出上下文腐化的存在。
